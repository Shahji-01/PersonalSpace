# Project audit — 9 October 2026

Compared the current checkout with `PersonalSpace-Specification-v1.2.md`, the four apps, ten shared packages, migrations, worker wiring, infrastructure and tests. This replaces the older coverage table: several features it listed as absent now have implementations. Code coverage and release acceptance remain separate.

## Assessment

PersonalSpace is a substantial development preview, not a completed v1.0 release. Notes/tasks and offline attachments have the deepest automated coverage. Learning, Money, preferences and account flows now have backend and mobile implementations, but significant delivery, privacy and native UX work remains. Production is still explicitly blocked in `packages/config/src/index.ts`.

The principal data path is mobile SQLite/outbox → API commands → PostgreSQL/RLS → entity/audit/outbox transaction → incremental sync. BullMQ workers handle file processing, exports and other background modules. The web app has landing/legal pages and a password-verified deletion request form; it is not the full web product (v1.1 scope).

## Confirmed operational gaps

These are source findings, not inferred from missing checkboxes:

1. **Background schedule registration:** maintenance, deletion, metadata, notifications and email repeat jobs are registered after the worker's `while (!stopping)` loop. A fresh worker therefore does not install those schedules while running. Existing Redis schedules may hide this. The new export relay and export expiry pass run inside the active loop.
2. **Deletion is incomplete:** `apps/worker/src/index.ts` still supplies a storage callback that only logs. The domain pipeline can mark completion without removing objects, and a process crash can strand a request in `processing`. Authentication anonymization does exist; the older audit's claim that it was wholly absent was wrong.
3. **Notifications do not yet send server pushes:** `deliverDueReminders` inserts pending log rows and advances reminder state, but has no push provider call. Device routes currently omit the `withUser` transaction required by RLS, use v7-only IDs against a v4 database default, and the client's watermark method sends POST to a PATCH route.
4. **Email delivery remains partial:** a Resend provider and auth enqueue hooks now exist. The fallback console provider logs recipient/body content, provider errors can be persisted verbatim, and failed messages lack a complete retry/claim lifecycle. Provider delivery and link completion have not been accepted.
5. **Retention needs correction:** `cleanupTrash` selects already-purged entities rather than items whose Trash age passed 30 days. Physical deletion of those reservations also needs to preserve offline retry/reference guarantees. Balance reconciliation writes computed values without proving protection against concurrent ledger mutations.
6. **Identity and UI promises exceed completion:** adding the JWT plugin does not establish rotating refresh families. The reset screen requests an email but does not yet provide the complete reset flow. Saved appearance/security preferences need behavior acceptance, not just successful persistence.

## Implemented in this pass: reliable export delivery and expiry

- Export creation and an `exports.generate` outbox event now commit atomically. The HTTP handler no longer creates a Redis connection or waits on queue availability.
- The restricted relay role publishes events with stable job IDs, acknowledges only after queue acceptance, and safely replays after a crash. Migration `0041_export_delivery.sql` recovers older queued requests without republishing completed jobs.
- Expiry honors the explicit download deadline as well as the 24-hour completion window. A bounded cleanup pass runs on worker startup and approximately once per minute while the loop progresses. Expired exports lose download access even when storage is unavailable.
- Cleanup only removes objects within the row's account/export namespace. It retains keys after failure, retries missing-object deletion safely and leaves live exports untouched. Provider response bodies are not logged by this cleanup path.
- This does not recover objects from superseded/crashed attempts whose keys are no longer tracked, restore a lost Redis dataset, or constitute complete account erasure. Storage/queue outages can delay physical cleanup; download authorization checks the deadline independently.

See [verification](verification.md) for exact checks. Apply migration 0041 before running the updated API/worker on another checkout. This pass uses isolated test databases and does not restart the user's running app or control the emulator.

## Implementation order

1. Repair device registration/watermark API and client behavior, then add real push delivery with retry/receipt coverage.
2. Repair background schedule startup together with retention/deletion safeguards; complete resumable object and account cleanup.
3. Complete identity recovery/OAuth callback/step-up flows, transactional email delivery and export policy/full-data coverage.
4. Complete mobile onboarding, Learning/player and Money workflows, shared settings behavior and accessibility. Validate on real Android/iOS devices when available.
5. Implement native capture/widgets, optional AI and the specification's evaluation gates.
6. Close infrastructure, security, performance, legal, beta and store acceptance.

No milestone is declared complete solely because its screens or tables exist. A percentage would obscure the remaining provider, device, privacy and release gates. The emulator remains untouched at the user's request.
